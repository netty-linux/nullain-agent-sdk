# P4.26 — Tool Search (Deferred Schemas) for MCP Scaling

> **Scaling property.** An MCP server's tools are registered with minimal
> metadata (name + description) and their full input schemas are **deferred**:
> a deferred tool is hidden from the LLM's tool list until the agent searches
> for it, at which point its schema is hydrated on demand. The agent discovers
> tools by name/description via a `search_tools` tool; only the schemas of the
> tools it actually selects are loaded into context.

## Why it matters

`register_mcp_tools` today calls `tools/list` and builds a full `ToolSpec`
(including the complete JSON input schema) for **every** remote tool, and the
agent loop sends **all** of those schemas to the LLM on **every** step
(`ToolRegistry.list_specs()` → `CompletionRequest.tools`). With many MCP servers
each exposing many tools, this is quadratic in the worst case: every schema is
fetched eagerly and re-sent every turn, even for tools the agent never uses.

Deferred schemas break that coupling:

- **Registration is cheap** — only names + descriptions are materialized; the
  full schema is fetched lazily, once, when a tool is actually selected.
- **The prompt is small** — a deferred tool is absent from `list_specs()` until
  hydrated, so the LLM only ever sees schemas for tools it has chosen to use.
- **Discovery is explicit** — the agent calls `search_tools(query)` to find
  relevant tools by name/description; the act of searching hydrates the matched
  tools' schemas so they become callable on the next step.

This is the same "tool search (schemas deferidos)" pattern Claude Code uses to
scale a large tool surface, and it composes with the P4.24 authority gate and
P4.25 plugin manifests unchanged (deferred registration is opt-in; the default
remains eager, so existing callers and the plugin loader are unaffected).

## Model

### `MCPClient.get_tool_schema(name)` — lazy single-tool fetch

MCP has no single-tool method, so this calls `tools/list` (cached after the
first fetch) and returns the matching `MCPToolDefinition`, raising
`MCPProtocolError` when the tool is absent. It is the deferred-schema primitive:
the full `input_schema` is fetched only when a tool is hydrated.

### `RegisteredTool.schema_loader` — deferred schema carrier

A `RegisteredTool` gains an optional `schema_loader: Callable[[], Awaitable[dict]]`
and two flags:

- `is_deferred` — `schema_loader is not None` (the schema is not eagerly present).
- `is_hydrated` — the schema has been loaded at least once.

`hydrate_schema()` is async, idempotent, and sets `spec.function.parameters`
from the loader's result. A deferred tool's `spec.function.parameters` starts as
`{}`; it is populated only on hydration.

### `ToolRegistry.search_tools(query)` + `hydrate_tool(name)`

- `search_tools(query)` — case-insensitive substring match over tool name and
  description, returning `list[ToolSearchResult]` (name, description, is_deferred,
  is_hydrated). This is the discovery primitive; it never loads schemas.
- `hydrate_tool(name)` — hydrate a deferred tool's schema on demand (no-op for
  non-deferred or already-hydrated tools).
- `list_specs()` — **skips unhydrated deferred tools.** A deferred tool is absent
  from the LLM's tool list until hydrated, so the model never sees a schema-less
  tool it might try to call with no arguments. Non-deferred tools are always
  included (backward compatible).

### `register_mcp_tools(..., defer_schemas: bool = False)`

When `defer_schemas=True`, each remote tool is registered with a `schema_loader`
that calls `client.get_tool_schema(remote_name)` and returns its `input_schema`;
`spec.function.parameters` is `{}` until hydrated. When `False` (the default),
behavior is unchanged (eager full schemas). The plugin loader (P4.25) and
existing callers keep the eager default.

## The `search_tools` agent tool

A built-in tool (in `nullain-tools`) that the agent calls to discover and
hydrate MCP tools:

```
search_tools(query: str, limit: int = 20) -> str
```

It searches the registry, hydrates the matched deferred tools (bounded by
`limit`), and returns a text summary of matches (name, description, hydration
state). Because the loop re-assembles `list_specs()` every step, the hydrated
tools become callable on the next step — the agent searches, then uses.

## Backward compatibility

- `defer_schemas` defaults to `False`; `register_mcp_tools` and the plugin
  loader are unchanged.
- `list_specs()` skips only unhydrated deferred tools; with no deferred tools
  registered, it returns exactly what it returned before.
- `RegisteredTool.schema_loader` defaults to `None`; `hydrate_schema()` is a
  no-op for non-deferred tools.
- `search_tools` is a new built-in tool; existing tool sets gain it without
  breaking existing calls.

## Honesty / scope

- **v1 defers the schema, not the tool list.** `tools/list` is still called once
  at registration to learn names + descriptions (MCP has no name-only listing).
  The win is prompt-size and per-tool schema materialization, not the single
  `tools/list` round-trip.
- **Search is substring-based** (name + description), not semantic. A
  description-embedding index is a documented follow-up; the registry/search
  surface is stable either way.
- **Hydration is all-or-nothing per match** (bounded by `limit`). A
  relevance-ranked partial hydration is a follow-up.

- `test_get_tool_schema_returns_matching_definition` — lazy single-tool fetch.
- `test_get_tool_schema_raises_when_absent` — unknown tool ⇒ `MCPProtocolError`.
- `test_register_deferred_hides_schema_until_hydrated` — `defer_schemas=True`
  registers with empty `parameters`; `list_specs()` omits it; `hydrate_tool`
  populates it and `list_specs()` then includes it.
- `test_register_eager_keeps_full_schema` — `defer_schemas=False` (default)
  registers with the full schema, unchanged.
- `test_search_tools_matches_name_and_description` — substring over name +
  description, case-insensitive.
- `test_search_tools_returns_hydration_state` — `ToolSearchResult` carries
  `is_deferred`/`is_hydrated`.
- `test_hydrate_tool_is_idempotent` — loader called once.
- `test_search_tools_tool_hydrates_matches` — the agent-facing tool hydrates
  matched deferred tools and returns a text summary.
- `test_list_specs_skips_unhydrated_deferred_only` — non-deferred tools always
  present; deferred tools appear only after hydration.
