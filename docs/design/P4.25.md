# P4.25 — Plugin Signing, SBOM, and Capability Manifests

> **Trust property.** A plugin is a signed, capability-manifested bundle of
> tools. Its identity, launch command, declared capabilities, tool
> declarations, and software bill of materials are pinned in a manifest whose
> signature covers a canonical serialization of all of them. The loader
> verifies the signature, intersects the plugin's declared capabilities with the
> operator's grant, and registers the tools — **fail-closed at every branch**.
>
> ```
> effective = plugin.capabilities ∧ operator_grant          # at load
> reachable = effective ∧ delegating_agent.authority         # at runtime (P4.24)
> ```

## Why it matters

A plugin (v1: an MCP server bundle) is the largest untrusted code surface the
harness loads. Without a trust anchor an operator who references a plugin is
trusting the launch command, the capability claims, and the dependency set
separately and silently — any of them can be substituted without notice.
P4.25 makes the manifest the single trust anchor: a signature over identity +
transport + capabilities + tool declarations + SBOM, so drift in *any* of them
invalidates the signature, and the operator's grant is intersected (never
unioned) with the plugin's claims.

This composes the two prior P4 guarantees around untrusted code:

- **P4.23 sandbox** confines the plugin subprocess (the OS-level boundary).
- **P4.24 authority-intersection law** confines what a delegating subagent may
  reach (the capability boundary). Plugin tools declare `requires`; the
  subagent authority gate intersects again at runtime, so a plugin tool is
  reachable only through **both** the operator grant AND the delegating agent's
  authority.

## Model (`nullain/plugins/`)

### `PluginManifest` — the trust anchor

```
schema_version: "nullain-plugin/0.1"
name, version, publisher, description
transport: PluginTransportDecl   # command + args + env — SIGNED, not in operator config
capabilities: frozenset[Capability]   # what the plugin declares it may exercise
tools: list[PluginToolDecl]      # per-tool requires + optional permission_level
sbom: SBOM                       # hashed dependency list
sbom_digest: str                 # pinned digest of sbom (carried explicitly)
signature: PluginSignature | None
```

`signed_message()` is the canonical bytes covered by the signature: the manifest
serialized with `signature` excluded and `sbom` collapsed to its pinned digest,
sorted-key compact JSON. The verifier recomputes exactly this message, so any
drift in identity, transport command, capabilities, tool declarations, or the
dependency list breaks the signature.

### `SBOM` — minimal, content-hashed

v1 is a structured, content-hashed dependency list (`SBOMDependency(name,
version, digest)`), not a full CycloneDX/SPDX document. `SBOM.digest()` is
canonical (dependencies sorted by name+version, sorted-key JSON) so signature
coverage is deterministic. Emitting CycloneDX/SPDX via the standard toolchain is
a documented follow-up; the digest scheme is stable either way.

### `SignatureVerifier` — hexagonal port

```
Protocol: available() -> bool; verify(manifest, trusted_keys) -> bool
Ed25519Verifier  — the nullain-sdk[signing] extra (cryptography), optional
NoVerifier       — fail-closed: never available, never verifies
select_verifier() — best available, falling back to NoVerifier
```

`cryptography` is an **optional** dependency (resolved via `importlib`, not a
static import, so the SDK installs cleanly without it). A signed plugin under
`NoVerifier` is **refused** — never loaded on trust — mirroring the P4.23
sandbox discipline.

## The load pipeline (`PluginLoader`)

Fail-closed, in order:

1. **validate** — schema version, `sbom.digest() == sbom_digest` (else
   `PluginSbomError`), and every tool's `requires ⊆ declared capabilities` (else
   `PluginManifestError` — a tool may not claim a capability the plugin did not
   declare).
2. **verify** — the signature. Signed + no verifier backend ⇒ refuse; signature
   mismatch / unknown key ⇒ refuse; unsigned + `require_signature=True` ⇒
   refuse. Unsigned + `require_signature=False` ⇒ load with a structured
   warning (trusted-local opt-in only).
3. **capability-intersect** — `effective = declared ∩ operator_grant` (the
   P4.24 meet for plugins). Tools whose `requires` exceed the effective set are
   **dropped with a structured log** (no silent truncation); if every tool is
   dropped, the plugin is refused (`PluginCapabilityError`).
4. **register** — the plugin's MCP server is launched and its tools registered
   (namespaced `mcp__<plugin>__<tool>`); each kept tool's `requires` and
   `permission_level` are overridden from the manifest. Undeclared tools default
   to `requires={WRITE}` (conservative, matching the MCP bridge).

`prepare()` runs steps 1–3 + MCP initialization **once** and returns a
`PreparedPlugin` (live client + baked-in `effective_capabilities`); `register()`
re-creates only the lightweight per-session wrappers, reusing the prepared
client across sessions (the subprocess persists).

## Operator config (`nullain.toml`)

The operator config **only** references the manifest path and narrows the grant;
it never carries the launch command (the signature covers the command,
preventing substitution):

```toml
[plugins]
enabled = true
require_signature = true
trusted_keys = { alpha = "base64-ed25519-pubkey..." }
allowed_capabilities = ["read", "write", "network"]

[plugins.entries.search]
manifest = "./plugins/search/plugin.json"
auto_approve = false
allowed_capabilities = ["read"]   # narrow this plugin's grant further
```

Per-entry `allowed_capabilities` **intersects** the global grant — an entry may
never widen what `[plugins].allowed_capabilities` grants. An unset global grant
means "no narrowing" (the universe, identity of the meet).

## Daemon wiring (`nullain_agentd/main.py`)

`_load_plugins` mirrors `_load_mcp_clients`: prepare once at startup, share
across sessions, and skip-with-structured-log any plugin that fails any pipeline
step (fail-closed **per plugin**, never fatal to the daemon — one bad plugin
does not prevent the rest from serving). Per-session, `plugin_registrar.register`
re-creates the wrappers; the per-entry narrowing is preserved because
`register()` uses the `PreparedPlugin`'s baked-in `effective_capabilities`. A
plugin that drops every tool at register time (e.g. the grant was narrowed
between prepare and register) is skipped with a log, not crashed. Plugin clients
are closed in the `finally` block alongside MCP clients.

## Backward compatibility

- `PluginsConfig` defaults to `enabled=True, entries={}` — no plugins configured
  ⇒ `_load_plugins` returns `[]`, daemon behavior unchanged.
- `PluginLoader.allowed_capabilities` defaulting to empty ⇒ everything dropped
  (the loader's own fail-closed default); the daemon explicitly passes the
  universe when the operator sets nothing, so unset-means-all is a config-layer
  convenience, not a loader invariant.
- `PluginManifest.signature` defaults to `None`; unsigned plugins load only
  under explicit `require_signature=false`.

## Honesty / scope

- **v1 plugins are MCP server bundles.** Native Python entry-point plugins (a
  bigger trust surface — in-process code, no transport boundary) are deferred.
  The manifest/signing/SBOM/capability machinery is transport-agnostic and will
  carry over.
- **Ed25519 is the only signature algorithm v1.** The `algorithm` field is
  versioned and extensible; a NoVerifier host refuses signed plugins rather than
  guessing.
- **SBOM v1 is a hashed dependency list**, not a full CycloneDX/SPDX document.
  It is content-hashed and signature-covered today; emitting the standard
  formats via the standard toolchain is a documented follow-up.
- **Capability hints for MCP tools are declared by the publisher** in the
  manifest (not introspected from the server). An undeclared tool is
  conservatively `WRITE`; a publisher who knows a tool is read-only declares it.
